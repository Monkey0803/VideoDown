| `presentation/MainActivity.kt`、`presentation/home/HomeScreen.kt` | 导入的链接直达批量导入对话框 |

### 设计取舍

- **每个字段可空。** 缺字段就保留当前值,而不是悄悄重置成默认——旧版本或新版本写的备份都能应用。
- **无法识别的值宁可丢掉。** `sanitized()` 会剔除未知枚举名（而不是猜测）、把并发数夹到 1–5、把超出上限的限速判为不可用、要求更新源是 http。手工改过的文件不该把应用置于自己的界面表达不出的状态。
- **导出目录权限故意不进备份。** SAF 授权属于单台设备,恢复后会变成悬空授权。
- **清单用纯文本。** 它唯一的用途就是重新导入,而 `#` 开头的注释行在读取时被忽略,所以文件本身也能读、能手改。

## C3 播放列表 / 合集批量下载

### 交付内容

| 文件 | 作用 |
| --- | --- |
| `data/generic/EngineRequest.kt` | 与 Python 引擎的请求契约(`parse`),含 `PLAYLIST_LIMIT = 20` |
| `data/generic/GenericVideoRepository.kt` | `playlistEnabled` 开关;请求改由 `EngineRequest.parse` 构造 |
| `assets/video_engine.py` | `noplaylist` 由「X 帖子」或「应用要求合集」决定;`playlistend` 取自请求 |
| `core/AppPreferences.kt` | `playlistParsing`(默认关闭)+ 纳入设置备份 |
| `presentation/settings/SettingsScreen.kt` | 「解析合集」开关与随状态变化的副标题 |

### 设计取舍

- **默认关闭。** 一个单视频链接不该悄悄变成二十条队列;打开开关才把整页条目交出来。
- **上限只有一处。** 设置页文案与请求里的 `playlist_limit` 共用 `EngineRequest.PLAYLIST_LIMIT`,不会出现「界面写 20、引擎收 100」。
- **契约提取成纯函数。** 引擎只能在设备上触达,一个悄悄不再发送的字段没有别的东西能发现,所以请求本身在 JVM 里断言。
- **逐条仍然是一条任务。** 引擎下载时按 `media_id` 只取选中的那一条(既有逻辑),条目身份不因合集而改变。

### 未覆盖边界

- **真实站点的合集只能离线验证到这个程度。** 本地页面证明的是「一页多条 → 多条可选可下」这条链路;需要登录、需要 JS 渲染或受地区限制的真实合集可能只返回部分条目,甚至与单视频一样只返回一条。`noplaylist` / `playlistend` 的语义按 yt-dlp 的既有行为使用,未对具体站点逐一验证。

## C2 字幕下载与内嵌

### 交付内容

| 文件 | 作用 |
| --- | --- |
| `assets/video_engine.py` | `public_info` 只把字幕的**语言名**交给应用；下载路径按请求下载字幕并显式添加 `FFmpegEmbedSubtitle` 后处理器 |
| `data/generic/EngineRequest.kt` | 下载请求契约，含 `subtitles` / `subtitle_langs` / `auto_captions` |
| `domain/model/SubtitleLanguageSelection.kt` | 纯逻辑：从可选语言里挑出要保存的轨，并给出界面文案 |
| `domain/model/DouyinVideo.kt`、`data/generic/GenericMetadataParser.kt` | 解析结果带上真实字幕语言与机器字幕语言 |
| `domain/model/DownloadRecord.kt`、`domain/repository/Downloader.kt`、`data/download/DownloadEngine.kt` | 把选择记在任务上，并让请求字幕的任务改走引擎下载 |
| `presentation/home/HomeScreen.kt`、`HomeViewModel.kt` | 结果页「同时保存字幕（中文）」选项 |

### 设计取舍

- **应用挑语言，不做逐语言勾选。** 一个源可能提供几十上百种语言（YouTube 自动字幕尤其夸张），全量抓取会把一次视频下载变成字幕仓库。规则：一个中文轨 + 一个英文轨（`zh-Hans` 优先于 `zh`，因为裸 `zh` 实际常是繁体），都没有时取源提供的第一个；**只有**在完全没有真实字幕轨时才退回机器字幕，文案上加「自动字幕 ·」前缀。
- **`live_chat` 不是字幕。** 提取器会把直播聊天回放列在字幕旁边,语言形状校验（`^[A-Za-z]{2,8}(-[A-Za-z0-9]{2,8})*$`）把它挡在外面。
- **请求字幕的任务改走引擎。** 字幕是提取器能力,而直链档位默认由 `ResumableDownloader` 传输——那样会「下载成功但文件里没有字幕」。引擎解析出来的直链档位一定带着来源页面,所以可以安全地交给引擎。
- **内嵌后删除字幕文件。** `already_have_subtitle=False`,因为一个任务只产出一个文件。
- **音频档位永远不取字幕**,内嵌进 m4a 没有意义;界面也不显示该选项。

### 排查记录：`embedsubtitles` 是空操作

第一版按 yt-dlp 文档传了 `"embedsubtitles": True`，设备上**下载成功、没有报错、文件里却没有字幕轨**。在设备上直接跑引擎自带的 yt-dlp（把 `--write-subs --embed-subs` 打到本地 `http.server`）看到字幕确实下载了、`[EmbedSubtitle]` 也确实执行了，只是缺 `--ffmpeg-location`；再读引擎里的 yt-dlp 源码（zipapp）确认：`yt_dlp/YoutubeDL.py` **完全没有** `embedsubtitles` 的引用，是 `yt_dlp/__init__.py`（命令行入口）把它翻译成 `FFmpegEmbedSubtitle` 后处理器。也就是说 Python API 传该键毫无作用。改为显式添加后处理器后立刻生效。README 的「已知限制」里记下了这一条，避免后人再踩。

### 未覆盖边界

- **真实站点的字幕可用性未离线验证。** 本地页面证明的是「声明了字幕 → 能挑语言 → 能下载并内嵌 → 播放器认得出」这条链路;需要登录、只给机器字幕或字幕另外计费的站点未逐一验证。
- **最多内嵌两条轨**（一个中文 + 一个英文），没有逐语言勾选界面。
- 字幕只走引擎路径:被 `probeDirect` 直接识别的裸视频链接没有提取器上下文,结果页不显示字幕选项。
- 任务卡片不显示「含字幕」,只能从播放页的字幕开关看出。
- 内嵌目标为 mp4/webm/mkv;mp4 里以 `text/3gpp-tt`(mov_text)存在。未验证 webm/mkv 目标的实际表现。

## C4 私有保险箱与应用锁

### 交付内容

| 文件 | 作用 |
| --- | --- |
| `domain/model/VaultPolicy.kt` | 纯逻辑：谁能看见、锁定时的文案、通知是否可深链、能否自动入库、链接是否可导出 |
| `domain/model/DownloadRecord.kt` | `isPrivate`（旧历史文件按 `false` 解码） |

| `presentation/library/LibraryQuery.kt` | 保险箱是独立视图：普通列表与保险箱各自只装自己那类条目，锁定时保险箱返回空 |
| `presentation/library/LibraryScreen.kt`、`LibraryActions.kt`、`LibraryOrganizationViewModel.kt`、`data/local/DownloadLibraryMetadataRepository.kt` | 入口、锁定、移入/移出；可见清单决定数量、分类下拉与批量操作 |

| `presentation/MainActivity.kt` | 首页「最近保存」不接收私密条目 |
| `data/download/DownloadCompletionNotifier.kt`、`DownloadService.kt` | 通知标题脱敏；私密完成通知不再深链到播放页 |
| `data/gallery/AutoGalleryExport.kt`、`data/backup/LinkList.kt` | 私密条目不自动进共享相册、不出现在导出的链接清单里 |

### 设计取舍

- **保险箱是独立视图，不是筛选器。** 普通列表永远不混入私密条目,解锁后也只显示私密条目;这样「数量」「分类下拉」与批量操作天然只针对可见集合,不需要在十几处分别加过滤。
- **一处决策,多处使用。** 可见性、锁定文案、通知文案、深链许可、自动入库许可、链接导出许可全部来自 `VaultPolicy`——隐私功能的失效点通常是"某条路径忘了脱敏",集中之后至少能被一个测试逐个覆盖。
- **通知一律按锁定态渲染**,不跟随"当前是否解锁":通知出现在锁屏上,而内存里的解锁状态不该决定别人能看到什么。
- **私密完成通知不深链。** 否则点一下通知就直接播了视频,绕过门禁;改为只打开应用。
- **移入保险箱不移动、不加密文件**,只改变它出现在哪里——这条写进了 README 的已知限制,避免误以为文件被加密。

### domain 与数据的两条边界（本批定下）

**一、domain 只留结构，不留文案。** `FailureGuidance(title, description, action, secondaryAction)` 把界面文案塞在框架无关的 domain 里，现在拆成：

- domain：`RecoveryAction`（去掉 `label`）+ `FailureActions(primary, secondary)`，只回答「有哪些可采取的动作」；
- presentation：`presentation/FailureText.kt` 用 `when` 把 `DownloadFailureKind`/`RecoveryAction` 映射到资源 id，并给出 `failureTitle` / `failureDescription` / `recoveryActionLabel` 三个组合函数。

测试随之改为断言**完整性**而不是句子：`DownloadFailureGuidanceTest` 现在断言每种 `DownloadFailureKind` 的标题与说明资源 id 互不相同且非 0、每种 kind 都有主动作、每种 `RecoveryAction` 都有文案 id——新分类漏翻译会直接失败。设备测试里原本写死的 `RecoveryAction.X.label` 也改成从资源读（`context.getString(recoveryActionRes(action))`），断言的仍是界面真正渲染的文字。

**二、数据不是文案。** `legacyFailureKind` 里的中文用于匹配**用户设备上已存的历史错误消息**（旧版本写进 `history.json` 的文本），翻译或改写会让旧记录无法识别。因此守卫测试支持按函数名豁免：

```kotlin
/** 这些函数里的中文是数据而非文案：它们匹配设备上已存的文本。 */
val DATA_FUNCTIONS = listOf("legacyFailureKind")
```

豁免必须写明理由、按函数名精确生效，并且**不得**用来放过任何界面文案。

### C1 收口：完成定义与「非文案」清单（第二十三批）

**完成定义**：所有**用户可见**文案都来自 `res/values/` 与 `res/values-en/`；`src/main/java` 里其余中文字面量逐条标注 `// l10n-ignore: <理由>`，守卫测试只统计未标注的串（当前 **0**）。两个语言文件各 622 条 key、一一对应。

**豁免只剩 2 处（不可本地化，理由是行为/兼容而非「不是文案」）**：

| 位置 | 为什么不能变成资源 |
| :--- | :--- |
| `GalleryExporter` 的 `"Music/拾影"` / `"Movies/拾影"` | 它们是 **MediaStore 目录名（路径）**，不是文案；跟随语言改变会把同一份文件写到不同目录，用户切换语言后文件「消失」 |
| `LinkList.HEADER` 的 `"# 拾影链接清单 v1"` | 它是清单**格式的标识行**，导入时会被再次解析；本地化会让另一种语言导出的清单无法导入 |

除此之外，`legacyFailureKind` 的 7 条历史消息匹配按**函数名**豁免（`DATA_FUNCTIONS`）——它们匹配旧版本已写进用户设备的文本。

**守卫机制的三条规则**（`LocalizationGuardTest`）：
1. `src/main/java` 里未标注的中文串数 ≤ `BUDGET`（现为 **0**，只许下降）；
2. `values/` 与 `values-en/` 的 key 必须一一对应（漏翻译会失败）；
3. `locales_config.xml` 必须声明 zh-CN 与 en（系统语言设置里才有的选）。

**这一批修掉的问题**：`LocalizationDeviceTest` 原本靠「等到中文标签『我的』出现」来判断界面切换，而标签现在会跟随语言——已改为用测试标签（`tab-bar` / `tab-settings`）定位，切语言的等待与点击都不再依赖文案。这正是这轮工作的主题：**测试也不应该依赖界面文案**。

### 存储动作、下载失败原因与 key 解析收口（第二十一批）

- `StorageViewModel` 是第四个被清掉句子的 ViewModel：`StorageNotice`（`InspectFailed` / `CleanIncomplete` / `Cleaned(数值)`）替代 `message: String?`；`StorageBudgetSummary` 的三个文案函数改成 `@Composable` 直接用资源（它本来就在 presentation 层）。
- `ResumableDownloader` 的失败原因改成 key（`download:resume_mismatch` / `empty_body` / `out_of_space` / `storage_write` / `network`）——这些会写进 `record.errorMessage`，因此必须走「存 key」约定。`AppError.Storage` 也补上了 `reasonKey`。
- **key 解析合并为单一入口** `core/reasonKeyRes(key)`，覆盖所有家族（engine/download/service/vault/gallery/x/platform/input/update/generic）；`storedErrorMessage` 变成一次查表。合并的直接收益：**存进记录的 key 不可能被原样显示**，不会再出现第二十批那种「新家族忘了加到解析器」的漏洞。
- 引擎里的 `CancellationException("用户暂停")` 与四条 `Log.w` 按既有约定就地标注 `l10n-ignore`（协程取消原因是诊断信息，从不作为文案显示）。
- `StorageBudgetSummaryTest` 改为断言数值（`storageBudgetFraction`、`storageBudgetShortfall`、headroom），文案由资源与编译期保证。

**分类修正（诚实记录）**：本批的粗分脚本把若干**用户可见**文案错分进了 C 类（例如 `GenericVideoRepository` 的「请输入 HTTP 或 HTTPS 视频网址」、`StorageSpaceGuard` 的「存储空间不足…」、`DownloadNetworkPolicy` 的「已暂停：仅在 Wi-Fi 下下载…」、`SleepTimer`/`PlayerGestures` 的秒数标签、`VaultPolicy` 的「保险箱内容」、两个 ViewModel 的提示）。这些按性质属于 B 类，**下一批继续迁移**；真正的 C 类只剩解析器兜底标题/画质标签、MediaStore 目录名、备份文件名，以及 `DownloadFailure` 的历史匹配（已豁免）。

### 剩余 142 条的构成与收口提案（第十九批起）

把剩余项按**性质**分完类（脚本按「是否出现在 `require`/`check`/`Log`/`throw ...Exception` 行」粗分，再人工复核）：

| 类别 | 数量 | 例子 | 建议 |
| :--- | ---: | :--- | :--- |
| A. 内部不变量与诊断 | 66 | `DownloadLibraryMetadataRepository` 的 `require("只可整理已保存文件")`、`XVideoHttpClient` 的 `IOException("X 短链跳转次数过多")`、`DownloadHistoryStore` 的 `Log` | **登记为「非文案」**（见下） |
| B. 仍是用户可见文案 | ~35 | `AppUpdateChecker`/`AppUpdateManifest` 的 6+2 条、`HomeViewModel` 的 3 条提示、`StorageViewModel` 的 4 条、`StorageBudgetSummary` 的 6 条、`ResumableDownloader`/`DownloadEngine` 写进记录的失败原因 | **继续迁移**（下一批） |
| C. 数据而非文案 | ~30 | `GalleryExporter` 的 `"Movies/拾影"`（MediaStore 目录名）、解析器的兜底标题（「微博视频」「X 用户」「抖音视频」）与画质兜底「原画」 | **保留并逐条登记理由**：目录名是路径、兜底标题会写进记录并成为文件名，翻译它们会让同一份内容因语言不同而落到不同目录/不同文件名 |
| D. 已豁免 | ~11 | `DownloadFailure.legacyFailureKind` 的历史消息匹配、日志行 | 已有 `DATA_FUNCTIONS` / `l10n-ignore` |

**收口提案（需要用户选择，二选一）：**

- **方案 1（推荐）：把 A 与 C 登记为「非文案」**，即在对应行加 `// l10n-ignore: <理由>`，并在验收记录里列出清单与理由；剩余计数将只统计 B。代价：约 96 行注释与一次全量复核；好处是**棘轮从此只统计真正的界面文案**，不会因为「翻译一条开发者断言」而虚增。
- **方案 2：把 A 也迁移**。代价：新增约 66 个 key（每种两语言）与一条 `require` 文案映射层；而 `require`/`check` 失败在界面上只会显示统一的「操作失败」，**没有用户可见收益**，且会给日志排查增加一次资源解析。

我倾向方案 1，并在 `docs/TODO.md` 里把 C1 的完成定义写成「所有用户可见文案均来自资源，其余逐条登记豁免」。**在用户答复前，A 与 C 都不改，也不计入已完成。**

### X 解析失败：类型化，并让 HTTP 状态归 HTTP（第十三批）

### 相册失败：从「比对文案」到「有类型」（第十二批）

`GalleryExporter` 用 `require(...)`/`IOException(中文)` 报错，而 `core.galleryErrorMessage()` 靠**把消息文本和 6 条中文字符串比对**来区分是哪种失败——这和第十批修掉的 HTTP 判定是同一个缺陷类：改动任何一句提示，归类就会静默变化。现在：

- `data/gallery/GalleryExportFailure.kt`：`enum GalleryExportFailure`（未完成/文件不存在/容器不支持/创建失败/写入失败/收尾失败/无权限）+ `GalleryExportException(failure)`；

### 持久化的错误存 key（第十一批）

`VideoEngineException` 原本把 14 条中文消息写死在异常里，`DownloadServiceException` 也是——而这些消息会被写进 `record.errorMessage` **持久化**。一个任务记录会活过用户切换语言，存句子等于把写入时的语言冻结下来。做法：

- `VideoEngineException(val kind)` / `DownloadServiceException(val failure: ServiceFailure)` 只带类型；
- 存进记录的値带前缀：`engine:<kind>`、`service:<name>`（`core/ErrorResources.kt`、`core/ServiceFailure.kt`）；
- 界面统一用 `storedErrorMessage(...)` 解析；**没有前缀的就是旧版本留下的中文消息**，原样显示，并且仍由已豁免的 `legacyFailureKind` 识别；
- 通知文案（正在下载/暂停/继续/全部暂停）改从资源取；日志行就地标注 `l10n-ignore`。

`AppError.Parse` 增加 `engineKind`，解析页的失败因此也能从资源出文案。**这一批要新增 26 条资源，并让 21 处 `VideoEngineException(...)` 的构造点与 5 处 `DownloadServiceException(...)` 全部改签名**；JVM 测试里断言超时文案的那处改为断言 `ServiceFailure.FOREGROUND_START`。

### 错误按状态、不按文案（第十批）

`DownloadEngine` 原先用 `outcome.error.message.contains("HTTP 403")` 判断是否重新解析原网址，用 `contains("HTTP 4")` 判断是否值得重试——**改一句提示就会悄悄改变重试行为**。这一批把它改成结构：

- `AppError.Http(code, cause, failureKind)`，`message` 固定为技术性的 `"HTTP $code"`（不是文案），状态码由 `downloadFailureKind()` 映射成失败分类；
- `ResumableDownloader` 返回 `AppError.Http`；引擎按 `httpStatus in setOf(401, 403, 410)` 重取、按 `httpStatus !in 400..499` 决定重试；
- 解析页的失败从 `errorMessage: String?` 改为 `error: HomeError?`（`FromApp` / `EmptyInput` / `NoVariant` / `QueueFailed`），文案集中在 `presentation/ErrorText.kt`。

**豁免机制也扩展了一条**：日志行可以就地标注 `// l10n-ignore: 说明`，守卫测试会跳过该行。日志是给开发者的，不是用户文案；就地标注让豁免在代码评审里可见，而不是把预算数字偷偷调高。

### 处理中的约定

- **文案进资源，代码里不留中文。** 格式串用 `%1$s` 占位；`ifBlank { }`、`semantics { }` 这类**非 @Composable lambda 里不能直接调 `stringResource`**，需要先取值再传入（解析页有 3 处 `semantics { contentDescription = ... }` 就是这么改的）。
- 空安全会让格式串报错：`stringResource(id, platformLabel)` 中的 `platformLabel` 即便上面判过 `isNullOrBlank()` 也不会被智能转换，要改写成 `if (...) stringResource(a) else stringResource(b, platformLabel)`。
- 每迁移完一个文件就**同一下调 `LocalizationGuardTest.BUDGET`**，让欠债只减不增。
- `domain/` 不能引用 Android 资源（仓库硬规则：domain 保持框架无关）。因此 `DownloadFailure`、`AppResult` 等 domain 里的用户可见文案改成了**稳定的 key / 值 / 枚举**，由表现层映射到资源；断言中文的 JVM 与设备用例已同步改为断言类型、结构或 key（**已完成**）。

### 方案 2：把「非文案」也做成资源（第二十四批）

用户要求连那 116 处豁免也搬进资源，因此做了这一批。**结果：豁免从 116 处降到 2 处**（外加按函数名豁免的 7 条历史匹配）。

**机制**：`core/AppText.kt` —— 应用级文本解析器，在 `VideoDownApp.onCreate` 里 `install(this)`。data/domain 的类**大多没有也不要 Context**（JVM 套件直接 new 它们，这正是它们可测的原因），为了几句话把 Context 穿过整个数据层不划算，所以用一个解析器。它为 `require`/`check` 消息、`IOException`/`CancellationException` 诊断、`Log` 日志、解析器的兜底标题与标签提供文案。

**JVM 测试的新做法**：`app/src/test/.../core/TestText.kt` 用反射把 `R.string` 的字段名装进 `AppText` 的测试缝，于是测试断言的是**用了哪条文案**而不是译文——例如 `assertEquals(listOf("media_label_animated(1)", "media_label_animated(2)"), …)`、`assertEquals("quality_original", variant.label)`、`startsWith("douyin_label_watermarked(")`。这比断言中文更稳：改译文不会让测试变红，改**用哪条文案**才会。

**已转换的类别与数量**：诊断异常 25、开发者日志 6、内部不变量 44、解析器兜底标题/画质标签等持久化内容 39（含把备份文件名改成资源、在设置页拼给系统选择器）。两个语言文件各 **720 条 key**。

**验证**：JVM 387 用例 0 失败（含守卫：未标注理由的中文串仍为 0）；模拟器 API 37 与真机 API 30 共 8 个套件 34 例 0 失败；把模拟器应用语言切成 en-US 后 dump 解析页 UI，**全部英文、无残留中文、无 `resource:<id>` 泄漏**（`AppText` 未安装时会返回该占位串，实测没有出现）。
